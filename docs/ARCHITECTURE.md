# Архитектура проекта `iptv-ru-monitor`

**Статус:** проектная архитектура, версия 1.0\
**Тип проекта:** публичный Open Source\
**Основная география:** Россия на первом этапе; расширение на другие
страны предусмотрено архитектурой\
**Инфраструктура:** GitHub Actions + российский VDS для географически
привязанных проверок\
**Цель:** собирать публичные IPTV-источники, проверять доступность и
качество потоков, сопоставлять EPG и логотипы, формировать плейлисты для
Android TV и TiviMate.

------------------------------------------------------------------------

## 1. Цели и границы проекта

`iptv-ru-monitor` --- автоматизированная система мониторинга публично
доступных IPTV-потоков и подготовки каталогов каналов.

Система должна:

1.  Собирать каналы из подключённых открытых источников и
    пользовательских списков.
2.  Нормализовать названия, страны, языки, категории и идентификаторы.
3.  Проверять HTTP/HLS-доступность, корректность плейлистов и
    медиапараметры.
4.  Оценивать качество и устойчивость по истории повторных проверок.
5.  Проверять доступность из России и, позднее, из других регионов.
6.  Сопоставлять каналы с EPG/XMLTV и логотипами.
7.  Генерировать M3U, XMLTV, JSON-каталог и отчёты.
8.  Автоматически публиковать результаты и сохранять историю.

### 1.1. Ограничения

Проект не обходит DRM, авторизацию, платные подписки или геоблокировки.
Он не предназначен для поиска и распространения нелегальных копий
платных каналов. Успешный HTTP-ответ не считается доказательством
воспроизводимости. Источники с неясными правами не включаются в
публичные сборки до проверки.

Лицензия самого проекта не распространяется автоматически на потоки,
EPG, логотипы и сторонние каталоги.

------------------------------------------------------------------------

## 2. Архитектурные принципы

-   **Source-first:** каждый канал и поток связан с источником
    происхождения.
-   **Канал отдельно от потока:** один канал может иметь несколько URL и
    вариантов качества.
-   **Повторяемые проверки:** единичный успешный запрос не доказывает
    стабильность.
-   **Географический контекст:** результат связан с регионом и точкой
    проверки.
-   **Воспроизводимые сборки:** одинаковые входные данные и конфигурация
    дают предсказуемый результат.
-   **Безопасная публикация:** секретные URL, токены и приватные данные
    не попадают в публичные артефакты.
-   **Расширяемость:** новые страны и источники подключаются
    конфигурацией и адаптерами.

## 5. Модель данных

Канал хранится отдельно от конкретных потоков: один канал может иметь
несколько URL, зеркал и вариантов качества.

### 5.1. Channel

  Поле                Назначение
  ------------------- ---------------------------
  `channel_id`        Внутренний стабильный ID
  `name`              Каноническое название
  `alt_names`         Альтернативные названия
  `country`           ISO 3166-1 alpha-2
  `languages`         Языки вещания
  `category`          Категория канала
  `tvg_id`            Идентификатор для EPG
  `logo_url`          URL логотипа
  `is_public`         Допуск к публичной сборке
  `metadata_source`   Происхождение метаданных

### 5.2. Stream

  Поле                   Назначение
  ---------------------- --------------------------------
  `stream_id`            Внутренний ID потока
  `channel_id`           Связанный канал
  `url`                  Адрес потока
  `protocol`             HLS, HTTP, MPEG-TS и т. п.
  `source_id`            Источник URL
  `declared_quality`     Заявленное качество
  `enabled`              Участвует ли поток в проверках
  `publication_status`   Допущен ли поток к публикации

Секретные URL и адреса с временными токенами нельзя сохранять в
публичном каталоге или логах. Для них по умолчанию запрещена публичная
публикация.

### 5.3. CheckResult

Одна запись --- одна проверка одного потока из одной точки наблюдения.

Поля:

-   `stream_id`, `checked_at`;
-   `probe_location` --- `github-runner`, `ru-vds` и т. п.;
-   `country_code`;
-   `http_status`, `dns_ok`, `tls_ok`;
-   `playlist_ok`, `first_segment_ok`;
-   `startup_time_ms`;
-   `video_codec`, `audio_codec`;
-   `width`, `height`, `fps`, `bitrate_bps`;
-   `duration_checked_seconds`;
-   `error_code`, `error_message`;
-   `check_version`.

### 5.4. EPG и логотипы

Сопоставление EPG выполняется сначала по `tvg_id`, затем по
нормализованному имени и таблице алиасов. Нечёткое совпадение не должно
автоматически перезаписывать ручное подтверждение.

Для сопоставления сохраняются исходный ID и название, выбранный
`channel_id`, способ сопоставления, уверенность, источник и признак
ручного подтверждения.

## 6. Источники данных и Discovery

Каждый источник реализует общий адаптер:

``` python
class SourceAdapter:
    source_id: str

    async def fetch(self) -> list["DiscoveredStream"]:
        """Получить записи каналов и потоков из источника."""
```

На первом этапе предлагается исследовать:

-   IPTV-org --- каталоги каналов и EPG;
-   Free-TV/IPTV --- дополнительный список открытых потоков;
-   собственные YAML/M3U-источники проекта.

Источники описываются в `config/sources.yaml`. Для каждого задаются тип,
URL, страна, период обновления, уровень доверия и политика публикации.

Пример:

``` yaml
sources:
  - id: iptv-org-ru
    adapter: iptv_org
    enabled: true
    country: RU
    public_policy: review
    url: "https://iptv-org.github.io/iptv/countries/ru.m3u"

  - id: free-tv
    adapter: free_tv
    enabled: true
    country: RU
    public_policy: review
```

Актуальность URL, структуру источника, лицензию и условия использования
необходимо проверить при реализации.

## 7. Проверка потоков

Проверки выполняются по уровням, чтобы не расходовать ресурсы на тяжёлую
диагностику заведомо неработающих URL.

### Уровень 1 --- быстрая проверка

-   DNS, TCP и TLS;
-   HTTP-код и заголовки;
-   редиректы и тайм-ауты;
-   размер и тип ответа.

### Уровень 2 --- HLS

-   разбор master/media playlist;
-   наличие вариантов качества;
-   доступность media playlist;
-   получение одного или нескольких сегментов;
-   корректность ссылок на сегменты;
-   ошибки и истечение токенов.

### Уровень 3 --- медиапроверка

Через FFprobe определяются наличие видео и аудио, кодеки, разрешение,
FPS и оценка битрейта. Для проверки запуска и декодирования можно
применять ограниченный по времени проход FFmpeg. Полное воспроизведение
каждого потока на каждом цикле не требуется.

### Уровень 4 --- повторяемость

Проверки повторяются с интервалами. Результаты связываются с точкой
наблюдения, временем и версией проверяющего кода. Один успешный запрос
не означает, что поток стабилен.

## 8. Географическая проверка и инфраструктура

Используются две независимые точки проверки.

### GitHub Actions

-   CI, линтеры и тесты;
-   сбор открытых источников;
-   базовая проверка URL;
-   сборка каталога и плейлистов;
-   публикация артефактов.

GitHub-hosted runner не считается российской точкой проверки. Его
результаты маркируются `github-runner`.

### Российский VDS

-   проверка доступности из российского сегмента сети;
-   проверка первого HLS-сегмента;
-   ограниченная медиапроверка через FFprobe;
-   передача результатов в общий процесс сборки.

GitHub Actions может запускать проверку по SSH или через защищённый
self-hosted runner. Для MVP предлагается Docker-окружение и отдельный
SSH-runner-скрипт; self-hosted runner можно рассмотреть позднее.

### Безопасность VDS

-   отдельный пользователь без root;
-   отдельный SSH-ключ CI с минимальными правами;
-   секреты только в GitHub Actions Secrets;
-   firewall и ротация ключей;
-   ограничения CPU, памяти, времени и параллелизма;
-   запрет выполнения команд, полученных из данных источников;
-   очистка токенов и приватных URL из логов.

Сторонний URL --- недоверенный ввод. Нужны SSRF-защита, проверка
редиректов и запрет обращения к localhost, приватным и служебным
IP-диапазонам, чтобы проверяющий не мог использоваться для доступа к
внутренним сервисам VDS.

## 9. Оценка качества и стабильности

Рейтинг строится по истории, а не по единичной проверке.

  Компонент                                            Начальный вес
  -------------------------------------------------- ---------------
  Доступность при повторных проверках                            35%
  Устойчивость получения сегментов / чтения потока               30%
  Время запуска                                                  15%
  Качество изображения и медиапараметры                          15%
  Корректность HLS                                                5%

Предварительные уровни:

       Балл Статус
  --------- -----------
    90--100 Excellent
     75--89 Good
     50--74 Unstable
      0--49 Failed

Веса --- стартовая гипотеза, которую нужно калибровать по реальным
результатам. Для нового потока с недостаточной историей используется
статус `Insufficient data`, а не необоснованно высокий балл.

Профили отбора задаются отдельно: `ru_default`, `ru_hd`, `ru_kids`,
`ru_sport`. Минимальные баллы и обязательные критерии настраиваются в
YAML.

## 10. EPG и логотипы

### EPG

-   загрузка XMLTV из настроенных источников;
-   проверка XML и временных зон;
-   точное сопоставление по `tvg_id`;
-   алиасы для альтернативных названий;
-   отчёт о каналах без EPG и неоднозначных совпадениях;
-   генерация XMLTV из разрешённых источников.

### Логотипы

-   приоритет логотипам из доверенных каталогов;
-   проверка MIME-типа, размера и доступности;
-   хранение URL и происхождения изображения;
-   отсутствие копирования в публичный каталог при неясных правах;
-   локальные переопределения через `config/logo_sources.yaml`.

## 11. Генерируемые артефакты

Для России:

``` text
dist/ru/
├── russia.m3u
├── russia-hd.m3u
├── russia-kids.m3u
├── russia-sport.m3u
├── russia.xml
├── channels.json
├── streams.json
└── report.json
```

-   `russia.m3u` --- основной плейлист для TiviMate и других
    IPTV-плееров;
-   тематические M3U --- отдельные подборки;
-   `russia.xml` --- XMLTV EPG;
-   `channels.json` --- нормализованный каталог каналов;
-   `streams.json` --- публичные сведения о потоках без секретов;
-   `report.json` --- машинно-читаемый отчёт проверок и качества.

В M3U формируются `tvg-id`, `tvg-name`, `tvg-logo`, `group-title` и
понятные названия. M3U и XMLTV используют согласованные ID.

## 12. CI/CD и расписание

  -----------------------------------------------------------------------
  Workflow                Назначение              Запуск
  ----------------------- ----------------------- -----------------------
  `ci.yml`                Линтеры, типизация,     Push / Pull Request
                          unit-тесты              

  `discover.yml`          Обновление каталогов    По расписанию и вручную
                          источников              

  `check-global.yml`      Базовая проверка из     По расписанию
                          GitHub Actions          

  `check-ru.yml`          Проверка из российского По расписанию
                          VDS                     

  `build-playlists.yml`   Объединение результатов После проверок
                          и генерация файлов      

  `publish-pages.yml`     Публикация сайта и      После сборки
                          артефактов              
  -----------------------------------------------------------------------

Начальный цикл:

1.  Ежедневное обновление источников.
2.  Несколько быстрых проверок в день.
3.  Проверки из российского VDS по ограниченному расписанию.
4.  Медиапроверки реже, чем HTTP/HLS.
5.  Публичная генерация только после применения политики публикации.
6.  Хранение истории с ограничением срока.

Расписание и параллелизм конфигурируются. Scheduled workflow в GitHub
Actions может запускаться с задержкой, поэтому точное время не
гарантируется.

## 13. Хранение результатов

Для MVP достаточно SQLite на VDS и/или JSONL-истории с периодической
агрегацией. Результаты GitHub Actions можно передавать как workflow
artifacts.

Разделение данных:

-   **Исходные данные:** загруженные каталоги и конфигурация.
-   **Текущее состояние:** каналы, потоки и активные статусы.
-   **История:** проверки с датами и точками наблюдения.
-   **Публикация:** очищенные публичные артефакты.

При росте нагрузки можно перейти на PostgreSQL. Брокер сообщений и
отдельная сложная инфраструктура для MVP не нужны.

## 16. Этапы разработки

### Этап 0 --- подготовка репозитория

-   создать публичный репозиторий `iptv-ru-monitor`;
-   добавить README, лицензию, CONTRIBUTING и SECURITY policy;
-   настроить Python-проект, форматирование, тесты и CI;
-   зафиксировать схемы данных и конфигурацию России.

### Этап 1 --- MVP Discovery

-   подключить один источник;
-   разобрать M3U;
-   создать нормализованные Channel и Stream;
-   устранить дубли;
-   сохранять происхождение каждой записи.

**Результат:** воспроизводимый JSON-каталог кандидатов.

### Этап 2 --- проверка потоков

-   HTTP/DNS/TLS checker;
-   HLS playlist и segment checker;
-   FFprobe;
-   тайм-ауты, лимиты и классификация ошибок;
-   JSON-отчёт.

**Результат:** отчёт о работоспособности потоков.

### Этап 3 --- российская точка проверки

-   подготовить Docker-окружение на VDS;
-   безопасно запускать проверки из GitHub Actions;
-   маркировать результаты по региону;
-   объединять результаты GitHub и VDS.

**Результат:** отдельная оценка доступности из России.

### Этап 4 --- EPG и логотипы

-   подключить XMLTV;
-   реализовать точное сопоставление по ID;
-   добавить алиасы и ручные переопределения;
-   сформировать отчёт о непокрытых каналах.

### Этап 5 --- рейтинг и плейлисты

-   реализовать накопительную оценку;
-   добавить профили качества и категорий;
-   генерировать M3U и XMLTV;
-   проверить совместимость с TiviMate.

### Этап 6 --- публикация и расширение стран

-   настроить GitHub Pages;
-   опубликовать каталог и отчёты;
-   добавить конфигурацию второй страны;
-   проверить, что логика стран не зашита в российский профиль.

## 17. Критерии готовности MVP

MVP готов, когда:

-   проект запускается локально одной документированной командой;
-   CI выполняет тесты на Pull Request;
-   источник IPTV подключается конфигурацией;
-   каналы и потоки нормализуются и дедуплицируются;
-   результат проверки содержит время и точку наблюдения;
-   HTTP/HLS/FFprobe-проверки имеют тайм-ауты и ограничения;
-   российская проверка выполняется на VDS и не смешивается с
    GitHub-runner;
-   M3U и XMLTV генерируются с согласованными ID;
-   публичная сборка исключает запрещённые и неясные по правам
    источники;
-   отчёт объясняет, почему поток включён или исключён;
-   README описывает ограничения проекта и подключение плейлиста в
    TiviMate.

## 20. Первые технические задачи

Рекомендуемый порядок Pull Request:

1.  `chore: initialize Python project and CI`
2.  `docs: add architecture and source policy`
3.  `feat: add channel and stream domain models`
4.  `feat: add IPTV-org M3U source adapter`
5.  `feat: add channel normalization and deduplication`
6.  `feat: add HTTP stream checker`
7.  `feat: add HLS playlist and segment checker`
8.  `feat: add FFprobe metadata probe`
9.  `feat: add JSON catalog and check report`
10. `feat: add Russian VDS check runner`

**Главный принцип:** сначала получить достоверный каталог потоков и
прозрачный отчёт проверок, и только затем собирать плейлист. Количество
каналов не является показателем качества --- приоритет у проверяемости,
стабильности, корректного EPG и допустимости источника.
