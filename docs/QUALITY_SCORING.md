# Оценка качества и стабильности

Рейтинг строится по **истории** проверок, а не по единичному запросу
(`src/iptv_monitor/scoring/`).

## Компоненты

| Компонент | Вес | Источник |
|-----------|-----|----------|
| Доступность при повторных проверках | 35% | доля проверок без `error_code` |
| Устойчивость получения сегментов / чтения потока | 30% | доля успешных сегментов (fallback: доля валидных playlist) |
| Время запуска | 15% | лучший `startup_time_ms`: ≤2 с → 100, ≥10 с → 0 |
| Качество изображения и медиапараметры | 15% | максимальное разрешение: ≥1080 → 100, ≥720 → 85, ≥576 → 65 |
| Корректность HLS | 5% | доля проверок с `playlist_ok` |

Веса задаются в `config/quality_profiles.yaml` (сумма = 1.0). Это **стартовая
гипотеза из архитектуры** — калибровать по реальным результатам.

## Нормализация весов (issue #21)

Балл — взвешенное среднее по **компонентам с данными**: сумма весов
компонентов, у которых есть данные, выравнивается к 1. Штатный конвейер
проверяет `http,hls` (ffprobe выключен по стоимости) — без нормализации
media-компонент (15%) был недостижим и максимум балла составлял 85, а
уровень `excellent` (90+) не брал никто. С нормализацией идеальный поток
штатного конвейера достигает 100.

Консервативное ограничение: если у потока **нет контентных доказательств**
— ни `stability`, ни `hls` (только HTTP-успехи: прямой TS, error page с
200, — HLS-уровень по протоколу не применим) — балл ограничивается
уровнем `unstable` (≤74). Публикация всё равно требует успешного
сегмента (`approval.require_segment`), такие потоки кандидатами не станут.

## Уровни

| Балл | Статус |
|------|--------|
| 90–100 | `excellent` |
| 75–89 | `good` |
| 50–74 | `unstable` |
| 0–49 | `failed` |

Для потока с числом проверок меньше `min_checks` профиля используется статус
**`insufficient_data`**, а не необоснованно высокий балл. Такие потоки не
попадают в публичные плейлисты.

## Профили отбора

Профили задаются в `config/quality_profiles.yaml` и описывают критерии
публикации: `min_score`, `min_checks`, опционально `min_height` (например,
`ru_hd` ≥ 720p) и `categories` (например, `ru_kids`, `ru_sport`).

## Калибровка

1. Накопите 1–2 недели истории (`data/state/checks.jsonl`).
2. Сравните распределение уровней с субъективной оценкой проигрывания
   в TiviMate.
3. Скорректируйте веса/пороги в YAML; пересоберите `iptv-monitor score` и
   `build` — история не пересчитывается задним числом, поэтому изменения
   видны на новых данных.
4. Фиксируйте изменения веса в коммитах с обоснованием.
